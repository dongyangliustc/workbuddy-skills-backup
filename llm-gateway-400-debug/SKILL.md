# LLM 网关 400 / 请求校验错误诊断

适用场景：自定义模型（OpenAI 兼容网关，LiteLLM / One-API / New-API / 自建 Rust 服务等）
出现 HTTP 400，且报错来自上游、客户端源码里找不到原因。

## 核心方法论（按此顺序，不要跳步）

1. **先拿错误原文，再谈假设。** 上游 400 的 message 几乎总是直接点名问题字段
   （如 `duplicate field \`reasoning_content\``、`Unsupported parameter(s): x`、
   `data did not match any variant of untagged enum X`）。
   客户端日志和源码检索都只能给间接证据。
2. **部署捕获代理拿真实流量。** 客户端实际发什么和你猜的往往差很远
   （本案例中，此前推断客户端会发 `truncation`/`safety_identifier`，
   真实请求里根本没有）。
3. **捕获必须"仅失败时落盘"。** 请求体含会话内容；只在响应非 200 时写该次请求体，
   成功请求永不落盘。这是隐私底线，也免去事后清理。
4. **用三组对照实验确证根因**：坏形态 / 只保留 A / 只保留 B。
   只有"复现错误"不算完，必须同时证明"去掉嫌疑即恢复"。
5. **用同一字节重放验证修复**：把捕获的失败请求原样经修复后的代理重放，
   400→200 才算闭环。这比让用户再试一次更硬。

## 典型根因模式（按命中率排序）

- **字段别名冲突**：上游 Rust(serde) 把 `foo` 声明为 `bar` 的 alias，
  客户端历史回传时两个都带 → `duplicate field \`bar\``。
  实测特征：只带其一都 200，同现必 400，且 0.1 秒内被拒。
- **字段值形态不符**：`reasoning_content` 这类字段常被上游定义为
  untagged enum（实测只接受字符串，数组/对象直接 400）。
- **客户端序列化 bug**：JS 客户端 `JSON.stringify` 不会产生重复键，
  所以重复键若真出现，多半是"alias 两键同现"或"值内嵌 JSON 再解析"。
- **参数白名单**：某些网关对未知参数直接 400（Responses API 专属字段
  `truncation`/`safety_identifier` 是常见雷）。
- 400 但延迟数百毫秒以上 → 可能是上下文超限或 token 计数后拒绝，
  与上述"秒拒"类区分开。

## 操作步骤

### 1. 部署捕获代理

```bash
python scripts/capture_proxy.py --port 8788 --upstream https://网关地址
# 把客户端配置的 baseUrl 改为 http://127.0.0.1:8788/
```

- 日志：`strip_proxy.log`，一行一请求：`方法 路径 fields=顶层字段 removed=变更 -> 状态 (耗时, 字节)`
- 失败请求体落盘：`capture/时间_状态_序号_req.json`
- 调试端点：`GET /_health`；`POST /_echo` 返回将要转发的（经过变换的）请求体，
  用于**离线验证变换逻辑，零模型调用**。
- 若已有明确的修复规则（删字段/改字段），写入脚本顶部 `STRIP_FIELDS` 或
  `sanitize_messages()`，规则要留注释说明实测依据。

### 2. 等待/触发一次失败，读日志

```
POST /chat/completions fields=messages,model,... removed=- -> 400 (107 ms, 1070 B)
    ERROR-BODY: {...上游错误原文...}
    CAPTURED-REQ: capture\111953_400_23992_req.json (216789 B)
```

注意 `removed=-` 说明客户端根本没发你怀疑的字段——这类"证伪"同样是关键产出。

### 3. 结构化分析（不读会话内容）

```bash
python scripts/analyze_capture.py capture/xxxx_req.json [可疑字段名]
```

输出：顶层键、消息条数、每条消息的 role 与**键名列表**（不打印值）、
重复键检测（object_pairs_hook）、可疑字段的出现偏移与类型。
重点看：消息里是否混入了客户端内部字段（messageId/traceId/usage/agent 等）、
可疑字段是"缺失/单现/双现"、值是什么类型。

### 4. 三组对照确证

```bash
python scripts/repro_template.py   # 复制模板, 填入三组 messages
```

模板自带：坏形态 / 只保留 A / 只保留 B。判定标准：坏形态 400 且错误原文与线上一致，
两组对照均 200。

### 5. 修复 + 重放验证

在代理里实现修复（如删除别名键）→ `POST /_echo` 离线确认变换正确 →
把**捕获的失败请求体原样**经代理重放，400→200 即闭环。

## 必踩的坑

- **本地端口被 env 代理劫持**：环境里常有 `http_proxy=127.0.0.1:xxxx`，
  urllib 会连本地端口的请求也发过去，表现为莫名其妙的 502 / os error 10061。
  代理内部访问上游、以及所有测试脚本，都要
  `build_opener(ProxyHandler({}))` 强制直连。
- **沙箱/会话后台进程会随会话结束而死**：诊断代理是长驻需求，
  会话内用后台任务拉起，长期方案交给启动项（登录触发）；
  用户长期不重启就会空窗，报"连接拒绝"时先查端口再查别的原因。
- **LiteLLM 会替你去重**：直接给上游发带重复键的请求可能得到 200，
  让你以为重复键无害。重复键真正致命是在"绕过 LiteLLM 重序列化"或
  "alias 两键同现（这连 LiteLLM 也救不了）"的场景。
- **合成 payload 打不出线上错误很正常**：不要在猜测里打转，
  尽早升级到"捕获真实请求体"。
- 限速：网关常见 20 rpm/key，对照实验每组间隔 ≥3.5 s，429 会污染结论。
- 捕获文件含会话内容：结案后征询用户是否删除 capture/ 目录。

## 结案产出建议

- 根因一句话 + 三组对照数据 + 重放前后对比（400→200）
- 明确区分"客户端 bug（应反馈上游修复）"与"网关侧问题（应联系管理员）"
- 代理保留作兜底 + 观测点，日志的 `removed=` 列可长期监控修复是否仍生效
