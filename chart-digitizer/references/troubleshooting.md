# 故障排查

按"现象 → 根因 → 处置"组织。每条都尽量给出可直接执行的命令。

---

## A. 检测阶段

### A1. `detect` 报面板数 = 0，但图上明显有坐标轴

**根因**（按概率排序）
1. 轴线被网格线/数据线干扰，长度占比不足
2. 图片有内边距裁切，轴线不贯通整幅图
3. 深底浅线（前景掩码方向反了）

**处置**
```bash
# ① 看诊断图确认轴线到底有没有被检出
chartdigit.py detect fig.png --diag d.png

# ② 放宽长度阈值（逐级试 0.1 / 0.08 / 0.05）
chartdigit.py detect fig.png --min-ratio 0.1

# ③ 干脆绕过检测，手动给数据区像素矩形
chartdigit.py extract fig.png --axes 78,15,575,392 --xlim 0 10 --ylim -1.2 1.2
```

数据区像素矩形怎么定？用画图工具/看图软件读出轴框内外沿的像素坐标，四边各向内缩 1–2px。

### A2. 检出面板数多于实际子图数

**根因**：图例框、插框（inset）、表格式注释被当作面板。

**处置**：用 `--panel N` 选正确的那一个；诊断图上会标出各面板编号。若目标面板没被检出，改用 `--axes`。

### A3. 面板顺序左右颠倒

**根因**：理论已用行容差聚类修正（见 `algorithms.md` §3.1）。若仍出现，说明该图行内 top 差超过 6px 容差。

**处置**：用 `--axes` 显式指定目标面板，或用 `--panel` 逐个确认。

### A4. `detect` 报倾斜角异常（如 90°/180°）

**根因**：已修正（`skew_degrees` 的取模逻辑）。若仍见异常值，说明检出的"轴线"实际是数据线或边框。

**处置**：看诊断图确认检出的是哪条线；用 `--axes` 手动指定。

### A5. 结构置信度低（< 0.5）

按 `SKILL.md` 的置信度表处理：必须看诊断图，不要盲信自动结果。低置信度常见于无轴框的散点图（只有两条 L 形轴线）——这类图轴线配对困难，直接 `--axes` 最省事。

## B. 提取阶段

### B1. 序列数多于真实曲线数（如 3 条曲线出 6 条）

有三个不同根因，先按下列顺序判别：

**① 抗锯齿边缘色**（最常见）
派生色带在空间上与纯色芯重合不足 70% 时会漏判。诊断：多出来的序列颜色明显比原曲线浅，且点数接近。

**② 散点标记的光晕**（仅散点图）
光晕位于标记**圆周**而非圆心，与标记中心的距离约等于标记半径，超出点对点容差。诊断：多出的序列颜色很浅（接近背景色），点数约为真实标记数的 1–2 倍。
已通过按标记半径放宽容差修正（见 `algorithms.md` §4.4.1）。若仍出现，说明标记半径异常大：

```bash
# 先看诊断图确认
chartdigit.py extract fig.png --xlim 0 10 --ylim 0 4 --diag d.png

# 或直接显式指定颜色，绕过主色聚类
chartdigit.py extract fig.png --colors '#d62728' '#1f77b4' \
    --names groupA groupB --xlim 0 10 --ylim 0 4
```

**③ 候选色吞掉背景**（最隐蔽）
某候选色与背景的距离刚好越过背景剔除阈值，但随后以匹配容差生成掩码时把**整个浅色背景**判为前景。
诊断特征很明确：**多出的那条序列点数极大**（接近提取区域的像素总数，如 72434 ≈ 73455），且覆盖范围几乎等于整个数据区。
已通过让剔除阈值与匹配容差恒等修正（见 `algorithms.md` §4.4.2）。

**通用收尾**：以上三种若都排除不掉，用 `--colors` 显式指定曲线颜色即可完全绕过颜色聚类。

### B1b. 只看输出说"序列数不对"时，如何快速区分②与③

看多出序列的**点数**：
- 点数与真实标记数同量级（十几到几十）→ ② 光晕
- 点数达到提取区域像素总数的量级（几万）→ ③ 吞背景

这是最快的判别方式，不需要读源码。

### B2. 序列数少于真实曲线数（同色多曲线被合并）

**根因**：`dedupe_series` 去重过度——两条真实曲线若绝大部分区间重叠，会被判为重复。

**处置**
```bash
chartdigit.py extract fig.png --no-dedupe --xlim 0 10 --ylim -1 1
```

### B3. 曲线范围被截断（y 上下界比图上窄）

**根因**：选错了颜色——保留了抗锯齿过渡色而非纯色芯。理论上已用背景显著性排序修正（见 `algorithms.md` §4.4）。若仍出现，通常是**背景色估计不准**导致排序退化。

**处置**：显式指定曲线颜色 `--colors '#rrggbb'`。颜色值可用看图工具取色，或先跑 `--diag` 看诊断图中标注的检出颜色。

### B4. 曲线陡峭段偏差大（最大偏差 3–5px）

**根因**：方法固有特性。陡峭段内 1px 的横向定位误差会放大成很大的纵向误差。

**说明**：这不是实现缺陷。RMSE 仍然很小（0.2–0.7px）。若陡峭段是关键区域，建议：

- 用 `--resample N` 重采样获得均匀 x 网格，再在数值上做处理
- 或提高源图分辨率（截取更清晰的版本）

### B5. 散点数翻倍 / 空心标记被拆开

**根因**：空心标记的中空处使连通域断裂。已用 `binary_closing` 迭代 2 次修正。

**处置**：若仍出现（标记中空过大），减小 `--min-points` 无效时应改用 `--kind scatter` 强制类型，并配合 API 里 `marker_max_size` 调参。

### B6. 图例被当作数据点提取

**根因**：图例中的线段/标记与曲线同色。

**处置（首选 · 文献 PDF 输入）**：用 `--exclude-from-pdf` 从 PDF 文本层取图例文字
与色块的 bbox，在连通域分析**之前**置为背景——这是**坐标排除**，不再依赖启发式：

```bash
chartdigit.py extract fig.png --axes L,T,R,B --xlim ... --ylim ... \
    --exclude-from-pdf paper.pdf --page 5 --rect L,T,R,B --format csv
```
此时产物里还会多出「图例」区块（条目名 + hex + 校验结论），可顺带核对配色。

**处置（图片输入 / 无 PDF 时）**：用 `--region` 把提取区域限制在数据区内（避开图例常处的角落），
或用 `--exclude` 手工给排除矩形（**图像像素**坐标，可多次给出，取并集）。
```bash
# 例：图例在右上，数据区 x 只取到 480px
chartdigit.py extract fig.png --region 78,15,480,392 --xlim 0 10 --ylim -1 1

# 或精确排除一个矩形区（与 --region 可并用）
chartdigit.py extract fig.png --exclude 420,20,470,70 --xlim 0 10 --ylim -1 1
```

### B7. 误检出文字标注为序列

**根因**：图中文字被着色（如红色注释）。

**处置（首选 · 文献 PDF 输入）**：`--exclude-from-pdf` 会自动把图内**所有**文字行 bbox
排除（轴标题、面板标签、图例文字一并处理），无需再手工试参数。

**处置（图片输入 / 无 PDF 时）**：提高 `--min-points`（默认 8）；文字连通域通常点数少。
```bash
chartdigit.py extract fig.png --min-points 20 --xlim 0 10 --ylim -1 1
```

### B8. 误差棒未被识别为误差棒

**根因**：形态判别阈值不合适——误差棒被当成折线，或中心点被吞进误差棒。

**处置**：调整高宽比阈值（默认 2.2）。误差棒细长则该值可以调小。
```bash
chartdigit.py extract fig.png --kind errorbar --errorbar-aspect 1.8 --xlim 0 10 --ylim 0 5
```

### B9. 数据区边缘曲线被截断（贴近轴线处丢点）

**根因**：`--inset` 默认内缩 2px 以避开轴框线，会切掉紧贴轴线的数据。

**处置**
```bash
chartdigit.py extract fig.png --inset 0 --xlim 0 10 --ylim 0 1
```
代价是轴框线本身可能被当成数据点，需在输出中剔除边界点。

### B10. 报"未提取到任何序列"，序列数 = 0（连通域被撑爆）

**根因**：**同色的多个元素在几何上连成一片** ⇒ `extract_series` 只拿到一个"超大连通域"，
`_infer_kind` 按形态把它判成 `errorbar`/`line`，随后 `_extract_one` 每列只取 1 点，
再经 `dedupe_series` 归零 ⇒ 链路以失败告终。两种高发场景：

1. **误差棒互相重叠**：近阈的多枚实验点挤在几十 meV 内，±25% 的误差棒彼此搭接，
   合并成一个面积上千 px² 的连通域（实测 area > 1900）。
2. **图内插图（inset）与主曲线同色且无背景遮罩**（见 **DP9**；实测 area = 9791、宽高比 0.51）。

**处置**：

- **先判这个连通域到底是不是你要的曲线。** 若它是"误差棒 + 标记"的混合物，auto 判别
  本来就无解——**不要继续调参**，改用该论文的**数值表格**（实验点通常在正文另有表）。
- 若它是被插图污染的**主曲线**，走 DP9 的置白/排除路径，并**显式给 `--kind line`**
  绕过 auto 判别。
- `--min-points` 只管"最少点数过滤"，**救不了这种归零**——别把它当解药。

## B-log. 对数轴

### BL1. 提取出的数值差了好几个数量级

**根因**：忘了加 `--log-x` / `--log-y`。工具默认两轴都是线性，用线性公式解读对数轴会得到
完全错误的数值——而且**输出的外观仍然正常**（数值单调、平滑、像真数据）。

实测对照（同一张半对数图，真值 y∈[0.051, 235]）：

| 命令 | 提取到的 y 范围 |
|------|---------------|
| `--ylim 0.01 1000 --log-y` | **[0.051, 234.6]** ✅ |
| `--ylim 0.01 1000`（漏了 `--log-y`） | **[141.4, 874.1]** ❌ |

注意第二行**连数值范围都完全错了**，但只要你不核对量级，它看起来毫无破绽。

**自检**：`extract` 的报告里有一行 `尺度=(linear,log)` / `尺度=(log,log)`。
**提取后先看这行**，确认与图的实际情况一致。

```bash
chartdigit.py extract fig.png --xlim 0 10 --ylim 0.01 1000 --log-y
```

### BL2. 范围该填什么？填真值，不是指数

常见误用是填指数：

```bash
--ylim -2 3      # ❌ 错：这不是对数轴的写法
--ylim 0.01 1000 # ✅ 对：填真实数值范围
```

`--log-y` 只是告诉工具"该轴是对数刻度，请按几何插值换算"，数值范围仍按图上刻度标签的
真实值给。混合轴（如半对数）只需加对应的那一个开关。

### BL3. 相对误差看起来很大（3%–5%），是坏了吗？

**不是。这是判据用错了。**

对数轴上 1 像素对应**固定的相对误差**，大小只取决于轴跨几个数量级：

| 轴跨数量级 | 1 像素的相对误差 |
|-----------|----------------|
| 5 | 3.0% |
| 3 | 1.8% |
| 1 | 0.6% |

所以跨 5 个数量级的图上「相对误差 3%」**恰好等于 1 像素**，属正常水平。
把它跟线性轴的「0.8px」直接比较是错的。

**正确判据**：

```
等效像素 = decade 误差 ÷ 每像素数量级
每像素数量级 = log10(ymax/ymin) / 轴高像素
```

本技能自检用例的实测值：半对数 0.32–0.81px，双对数 0.61–0.86px，与线性轴同量级。

> 这个坑我自己踩过：早期验证脚本用「相对误差 < 1%」做判据，在跨 5 个数量级的图上
> 得出"未达标"的错误结论，差点去改一个本来就正确的实现。

### BL4. 对数轴图多检出 1 条序列（浅色"伪折线"）

**根因**：浅色抗锯齿候选色在 `tol=64` 内吞掉了浅灰网格线。已由 `drop_antialias_colors`
在生成掩码前修正。

**注意该缺陷是间歇性的**——取决于光晕色到网格灰的距离是否小于 64（实测 52.9 触发、
67.2 不触发，仅因图几何不同）。所以判断时要看具体图：

```bash
chartdigit.py extract fig.png --log-y --xlim 0 10 --ylim 0.01 1000 --diag d.png
# 若多出的序列颜色很浅、且点数与区域宽度同量级 → 网格线被吞
```

**处置**：用 `--colors '#d62728'` 显式指定曲线颜色即可完全绕过颜色聚类。
若确认为本缺陷复发，请补充 `tests/test_extract_units.py` 的用例并报告。

## B-audit. 标定审核

### AU1. 审核块报「该轴很可能不是线性刻度」

**含义**：工具检出的刻度**非等距且非整数倍**。线性轴的刻度必然等距或成整数倍，因此这是一条
可靠的**单向**证据——该轴不是线性刻度。绝大多数情况就是漏加 `--log-x` / `--log-y`。
同时输出的「按当前标定换算的刻度值」会给出直接证据：

| 图 | 声明 | 算出的刻度值 | 图上印的 |
|----|------|-------------|---------|
| 半对数 y | `linear` ❌ | 0.01 / 200.5 / 401 / 601.5 / 802 / 1002.6 | 10⁻²…10³ |
| 半对数 y | `log` ✅ | 0.01 / 0.1006 / 1.0119 / 10.18 / 102.4 / 1030 | 10⁻²…10³ |

**处置**：加 `--log-y`（或 `--log-x`）重跑。若确认图确实是线性轴而警告不消失，见 AU6。

### AU2. 审核块报「尺度取自默认值（线性），您未明确声明」

**含义**：该轴没给 `--log-x/--log-y`，也没给 `--scale-x/--scale-y`，工具用了默认值 `linear`。
这不是错误，而是提示"这件事您没想过"。默认的 `linear` 是最危险的默认值。

**处置**：确认后显式声明以消除歧义（审核块随即标为「用户指定」）：

```bash
--scale-x linear --scale-y linear
```

声明线性还有一个附带好处：配合 `--confirm-scale` 后，JSON 里 `ready_for_downstream` 才为
`true`，下游可以据此做机器判定。

### AU3. 审核块报「警告: 无」，但仍不放心

工具只能判断"间距模式与声明的尺度是否自洽"，**不能**读取刻度标签上的数字——数值范围本身
永远需要人来核对。最短的闭环检查是：把审核块里「按当前标定换算的刻度值」与图中同位置印的
数字逐一对齐。**任一对不上即说明尺度或范围有误**（先查 ×10ⁿ 量级标注与物理单位）。

需要更强保证时，走 GetData GUI 目视复核（见上文 C 节）。

### AU4. `--strict-scale` 返回退出码 4，且没有产物

**这是设计行为**，不是失败：审核有警告且无人签字时，严格模式拒绝写出交付物——避免"看起来
能用"的半成品流到下游。退出码约定：`0` 正常 / `1` 用法错误 / `2` 提取失败 /
`3` 未找到 GetData / **`4` 待人工审核**。

**处置**：逐条核对警告；确认无误后加 `--confirm-scale` 重跑。人工确认可越过警告——机器报警，
人签字负责。

### AU5. 明明是对数轴，却只给了软提示「请目视确认」

**这是数学事实，不是缺陷。** 仅含整数量级主刻度的对数轴（如只有 10⁻²、10⁻¹、10⁰、10¹、10²），
其刻度位置与线性轴**完全同形**，任何几何方法都无法区分。工具不假装能区分，直说"工具无法替您
排除"。

对数轴之所以通常能被识破，靠的是**次刻度**（每数量级内 2..9 位置的短刻度）——它们的间距
非等距。若某张对数图未绘制次刻度，就只剩人工确认这一条路。

**处置**：目视核对图中的量级标注（`10ⁿ` 形式），加 `--log-y --confirm-scale`。

### AU6. 线性轴被误报「很可能不是线性刻度」

**根因**（按可能性排序）：

1. **曲线恰好贴着轴线**：贴轴处的少量像素被计为一个"刻度"，使间距失去规律。
2. **图例/标注文字压在轴线附近**：文字笔画被计为刻度。工具已用自适应扫描带规避
   （实测标签起于轴外约 10px，而刻度本体只占 1..4px），但极端紧凑的排版仍可能穿透。
3. **主刻度与次刻度混排**（如 `0, 0.5, 1, 1.5` 同时有 `0.25, 0.75` 的短刻度）：这其实是
   等距的，但若只有部分被检出，间距会显得无规律。

**处置**：先看 `--diag` 诊断图（诊断图上叠加了检出刻度）。确认是误报后：

```bash
--confirm-scale     # 签字越过
```

若同类图反复误报，属于刻度检出缺陷，请按 `tests/test_audit_units.py` 的写法补一条确定性
用例（合成数组构造几何，不要用光栅化图），再修 `detect.auto_tick_band` / `find_ticks`。

> 回归红线：**修改刻度检测后，必须用真实图复跑并确认线性轴仍判 `uniform`**。
> 实测基线（六张测试图的 `ticks_for_box` 结果）：
> A/B/C 两轴均 `uniform`；E 的 x 轴 `uniform`、y 轴 `nonuniform`；F 两轴均 `nonuniform`。
> 线性轴一旦开始出现 `nonuniform`，就意味着硬警告会产生误报。

### AU7. 拟合残差很小，能证明对数轴标定对吗？（**不能**）

**这是最危险的一类假阳性。** 残差只证明"刻度的**几何位置**被量准了"，**不**证明
"哪个像素对应哪个数量级"。量级对错时曲线形状依旧平滑好看，数值却差 3–5 个数量级（BL1）。
只有图内印有 `10ⁿ` 标签时，工具才拿得到量级；未印时**必须**另建独立证据链。

**唯一可靠的闭环 = 用一个能从图中"独立算出"的已知量反解，再与其文献值比对。**
实测有效的两种（Douguet 2014, Figs 4/8/11 总光脱附截面）：

1. **终点闭合**：模型曲线在阈值以上的终点若有解析式（如 `σ = σ∞·√(1−E₀/E)`），可反解阈值
   `E₀` 与文献比。实测 C₄H⁻ 反解 **3.5591 eV** vs 文献 3.561（**0.05%**）、
   C₆H⁻ **3.7966** vs 3.796（**0.02%**）—— 这条**同时验了 y 轴量级与 x 轴锚点**。
2. **跨源对照**：把图内标记反算成 (x, y) 后与该论文**数值表**逐点比。实测 C₄H⁻
   3.790/4.032 eV、C₆H⁻ 3.860/4.030 eV（ΔE ≤ **1.5 meV**）；C₂H⁻@4.03 = 5.054 Mbarn
   vs 表 5.05（**+0.1%**）。

**纪律**：对数轴交付物**必须**带一条这样的闭合证据；只报"残差 ≤0.006 pt"**不合格**。

## C. GetData 联用

### C1. GetData 打开工作区弹出 "Unable to open file"

**根因**：`<File><Name>` 相对路径是相对于 **GetData 进程的 CWD**，不是 `.gdw` 所在目录。见 `references/gdw-format.md` §3.2。

**处置**：本技能生成工作区时已一律写绝对路径。若工作区是手工编辑的，检查 `<Name>` 是否为绝对路径。

### C2. PNG 图无法在 GetData 中打开

**根因**：GetData 2.24 原生不支持 PNG（仅 JPG/TIF/BMP/PCX）。见 `gdw-format.md` §3.3。

**处置**：无需人工干预——`build_workspace()` 会自动转 BMP。但如果**手工**构造 `.gdw`，必须先自行转换并在 `<Name>` 中指向 BMP。

### C3. GetData 复核后回读的数据与 native 结果有约 0.003 的偏差

**根因**：GetData 会把锚点像素坐标**截断为整数**，导致它内部重投影点集时产生偏差。见 `gdw-format.md` §3.1。

**处置**：`getdata.py::_rounded_calibration()` 已处理（先把锚点取整，再用取整后的锚点反投影所有点，使工作区内部自洽），实测偏差降至 3.2e-05。

若偏差仍偏大，说明该工作区是**旧版本生成**或**手工修改过锚点**——重新用 `to-gdw` 生成一次即可。

### C4. 找不到 GetData 可执行文件

```bash
chartdigit.py doctor
```
若报 `exe_found: false`，显式指定：
```bash
chartdigit.py extract fig.png --exe "D:\Program Files (x86)\GetData\GetDataW.exe" ...
```
或设环境变量 `GETDATA_EXE`。

### C5. `--open` 后命令不返回

行为说明：`--open` 默认不等待（`wait=False`），应能立即返回。若加 `--wait` 则会阻塞到 GUI 关闭——不要在与自动化串联时使用 `--wait`。

## D-pdf. 文献 PDF

面向 `from-pdf` / `--exclude-from-pdf` 这条前置链路（原理见 `references/pdf-legend.md`）。
**总原则：图例与排除掩码都是可选增强，任何失败都只告警、不改链路结局**；只有"用法错误"
（缺参数、`--dpi` 低于 300）才是非 0 退出码。

### DP1. 图定位失败（`from-pdf --figure N` 退出码 1，或 `--list` 一张图都没列出）

**根因**（三通道各自的失效场景）：

| 通道 | 失效场景 |
|------|---------|
| A 图注锚定 | 扫描件 / 无图注编号（P1 实测：正文是图片，全篇 **0 行**图注） |
| B 位图 bbox | 现代期刊插图为**矢量图**，`type==1` 的 block 根本没有（P3 单页矢量对象 9728 个、位图仅 11 个） |
| C 矢量簇 | 整页被正文矢量化时会给出越界的大簇（置信度上限只有 0.4） |

**处置**：`--list` 是**无副作用**的（不写文件、除 PDF 打不开外永远退出码 0），可随时跑，
先把候选与来源通道打出来；定位不到就**换通道**或**手工框选**：

```bash
PY=".../python.exe"; SKILL=".../scripts"; PDF="paper.pdf"

# 1) 看候选（页码 1 起、bbox 是 PDF 点坐标、来源=caption/raster/vector-cluster）
"$PY" "$SKILL/chartdigit.py" from-pdf "$PDF" --list

# 2) 手工框选（唯一的兜底路径，工具绝不猜）
"$PY" "$SKILL/chartdigit.py" from-pdf "$PDF" --page 5 --rect 48.64,51.99,288.40,368.79 -o fig
```

`--rect` 的四个数是 **PDF 点坐标**（同 `--list` 打印的 `bbox_pt`），y 自页顶向下。
不知道矩形时，把该页渲染出来目视量取（`detect --diag` 只作用于裁好的图片，帮不上这里）。

### DP2. 同一编号有多个候选 → 报"歧义"（退出码 1）

**根因**：图号在同一 PDF 里可重复出现——正文引用（`as shown in Figure 3 ...`）、
分页页眉、以及**表注与图注同号**（P2 实测：`Figure 1` 与 `TABLE 1` 并存）。

**处置**：工具已做两道消歧（正则前瞻 + 图注消歧门 G1/G2/G3）并给表注独立命名空间
（`T1`），但**歧义时一律报错而不选"最像的"**。按提示改用 `--page` + `--rect`。
若只是正文引用被误纳，用 `--list` 核对 `来源` 与置信度：`caption` 且置信度 0.90–0.95
才是图注锚定的结果；`vector-cluster` 恒为 0.40，属兜底噪声。

### DP3. 图例不存在（`legend.found=False`）

**这是最高频的结局，不是缺陷。** 期刊常把颜色含义写进**图注文字**而不画图例。实测：

| 图 | 图例 | 说明 |
|----|------|------|
| P3 `Fig. 2` | ✅ 检出 3 条 | 图内画了色块 + 6.6 pt 文字 |
| P3 `Fig. 3` / `Fig. 5` | ❌ | 图注里写 `red markers L-Pro, blue D-Pro`，图内无图例 |
| P2 `Fig. 2`（2007 年） | ❌ | 插图是位图，图内无文本层 |
| P1（扫描页） | ❌ | 整页是位图，无文本层 |

**处置**：**什么都不用做** —— 链路照常产出，只是序列名为自动配色名（`c1_3f3fff`）。
若图注文字里写了颜色含义，由人工读图注后改用显式 `--colors` / `--names`：

```bash
"$PY" "$SKILL/chartdigit.py" extract fig.png --axes ... --xlim ... --ylim ... \
    --colors '#ff3f3f' '#3f3fff' --names 'L-Pro' 'D-Pro' --format csv
```

> 用图注文字自动解析颜色含义**不在本技能范围内**（那是语义理解，不是几何/文本层提取），
> 但人工读一眼图注再手敲 `--colors` 成本极低。

### DP4. 颜色校验失败（`color_check.ok=False`，报告写着"已回退自动配色"）

**根因**：图例色块的 RGB ≠ 图内曲线的 RGB。期刊可能对图例做淡化、换色、加边框。
这是本方案**唯一会静默出错**的风险点——按图例颜色去取色可能一条曲线都提不到，
所以宁可不通过校验也不硬用。

排查顺序（报告里已给出图例色与图内实际主色的对照，照着看即可）：

1. **对照报告里的两组颜色**。若图例给 `#7f7fff` 而图内主色是 `#7f7fff` 的邻域 → 大概率是
   **区域取错**（见第 3 条）；若两者明显不同族 → 期刊确实改过色块，**回退是正确结局**。
2. **看 `missing` 点名了哪个色**。`ok=False` 且 `checked=3 matched=2` 说明只有一条不匹配，
   通常是该曲线被别的曲线**遮住**（见 DP6）或该色在图例里但没画进这个面板。
3. **确认 region 是否与图例同图**。`--exclude-from-pdf` 的 `--page`/`--rect` 必须与
   该 PNG 同源。跨图套用（拿 A 图的图例去解释 B 图）必然失败——这是**正确**的失败。
4. **色块"喂饱"校验的加固项**。校验会剔除图例色块自身后再统计（`plot_hits`）。
   若某色的命中**只**来自色块本身，`plot_hits=0` → `usable=False`。属预期行为。

**处置**：接受回退（默认，退出码仍为 0），或人工确认配色后显式给 `--colors`。
**不要**为了让校验通过而放宽 `--tol`——那会把"颜色不存在"变成"颜色差不多"。

### DP5. 面板拓扑为开放脊（只有左 + 下脊）→ `detect` 报"轴框未闭合"

**根因**：`find_panels` 依赖长轴线**配对**构成闭合/近闭合矩形。而"多条堆叠、共用 x 轴、
仅左+下开放脊"的排版（P3 `Fig. 2` 实测即是：三个 79.2 pt 高的面板、间距 13.2 pt、
只有一条共用底轴；顶面板的左脊还比下面两个**偏右 1.9 pt**）没有闭合框，于是：

```
面板数: 1
  [open-axes] box=(...)  开放 边=['bottom', 'left']  内容占比=0.186
  ⚠ 轴框未闭合（仅检出部分边），数据区上/右边界为推断值，建议人工确认
```

**处置**：**逐面板手工给 `--axes`**，每个面板单独标定（各面板纵轴范围通常不同）。
从 PDF 的矢量对象取几何是最可靠的量法：

```bash
# 在 Python 里用 pymupdf 直接量：垂直长线给面板的 y 区间与左脊 x，水平长线给共用 x 轴
"$PY" -c "
import pymupdf
pg = pymupdf.open('paper.pdf')[4]
R = pymupdf.Rect(48.64, 51.99, 288.40, 368.79)          # from-pdf 给的图矩形
for d in pg.get_drawings():
    r = d['rect']
    if not (r.x0>=R.x0-2 and r.y0>=R.y0-2 and r.x1<=R.x1+2 and r.y1<=R.y1+2): continue
    if r.width > 100 and r.height < 2.5:  print('水平轴 y=%.2f x=[%.2f,%.2f]' % (r.y0, r.x0, r.x1))
    if r.height > 20  and r.width  < 2.5: print('左脊   x=%.2f y=[%.2f,%.2f]' % (r.x0, r.y0, r.y1))
"
```

再把 PDF 点换算成裁图像素（`px = (pt − rect左/上) × dpi/72`），逐面板传 `--axes`。
横轴用**同一套**标定（共用轴），纵轴各面板分别给：

```bash
"$PY" "$SKILL/chartdigit.py" extract P3_Fig2.png \
    --axes 226,199,1989,859 --xlim 7.6202 11.5633 --ylim 0 1 --kind line \
    --exclude-from-pdf "$PDF" --page 5 --rect 48.64,51.99,288.40,368.79 \
    --format csv xlsx json -o panel1
```

> **`--kind auto` 会误判被遮挡切断的陡曲线（R8，已知缺陷，未修，仅锁定）。**
> 实测：某条陡曲线被相邻曲线遮挡切成数段后，**每一段**都成为高宽比 > 2.2 的细高连通域，
> `_infer_kind` 的判据 `tall >= max(3, 0.25*len(props))` 因此被跨过 → 判为 `errorbar`。
> 两种后果：段数 < `min_points` 时该序列**整条丢失**（同一张图另两条正常）；段数够多时
> 序列被保住但**标签错、点数错**（"点"是各段质心，一段一个点）。
>
> **根因是「被切断」，不是「陡」**——单条未打断的陡曲线只有 1 个细高分量，`1 < 3`，仍判
> `line`。因此**遮挡状况一变，表现就变**，不能靠"目测够陡"判断会不会踩到。
>
> **处置**：这类连续曲线图**一律显式给 `--kind line`**。
> 判别现象：报告里的序列数少于图例条目数，且少的那条正是最陡/被遮挡最多的那条。
> 机制、合成夹具证据与 13 项锁定断言见 `pdf-legend.md` §16.6；
> 锁定测试为 `tests/test_extract_units.py::test_kind_auto_steep_fragmented_curve`。
> **修 `_infer_kind` 属改动既有判定逻辑，须单独立项**（当前 S3 权限只允许追加测试与文档）。

### DP6. 序列数少于图例条目数（曲线被遮挡 / 被裁剪）

**根因**：图例说有 3 条线，实际只提到 2 条。常见三种原因：

1. **遮挡**：曲线互相重叠处只画了最上面那条，下面那条的像素不存在。实测 P3 `Fig. 2` 的
   红线 `RH` 在 10.1 eV 以上完全被绿线盖住，提取的 x 区间只到 10.107 eV。
2. **叠加**：几条曲线在低能端完全重合于基线，各自的颜色掩码被切断。
3. **`--kind` 误判**（见 DP5 末尾）。

**处置**：**这是物理限制，不是缺陷** —— 只有可见像素才能被数字化。
在交付说明里如实写明"该序列仅在 x ∈ […] 区间可见（被同图其他曲线遮挡）"，
**不要**用插值把缺口补上。需要完整曲线时只能回到原始数据（作者处）或改用可分辨的图源。

### DP7. 图定位/裁剪正常，但产物里没有「图例」区块

**根因**：图例区块**只由 `--exclude-from-pdf` 路径产生**。没有这个开关时，
产物与改动前完全一致（这是回归红线）。

**处置**：确认命令里带了 `--exclude-from-pdf` **且**同时给了 `--page`/`--rect`
（缺任一个 → 退出码 1，用法错误）。若带了却仍无区块，看 stderr 的告警：
PDF 打不开 / 页码越界 / `pymupdf` 不可用，都会**静默回退**并给出告警。

### DP8. 文献被移动导致第 8 阶段冒烟测试跳过

**现象**：`run_all.py` 报 `PDF 真实文献冒烟 ... 通过`，但仔细看输出是
`（跳过：文献不存在）`，且"跳过 1 项（不计入检查数）"。

**根因**：`test_pdf_smoke.py` 依赖三份外部文献的**绝对路径**（P1/P2/P3）。按设计，
文件不存在时打印跳过并计为**通过**（否则文献一移动测试就全红）。

**处置**：这是**有意设计**，但意味着**第 8 阶段的覆盖度会随环境静默变化**。
看到"全部阶段通过"时请顺手确认这 24 项是**真的跑了**而不是跳过了：

```bash

# 期望看到：P1/P2/P3 均为「存在」，且末尾「共 24 项检查，失败 0 项」
```

若要恢复覆盖，把三份文献放回 `tests/test_pdf_smoke.py` 顶部的 `REAL_PDFS` 所列路径，
或修改该常量指向本机现有文献（需保持"一页矢量图 + 一页扫描位图"的搭配以覆盖两条通道）。

### DP9. 图内插图（inset）与主曲线同色 → 主曲线被污染、序列归零

**现象**：`extract` 报"未提取到任何序列"（提取失败），或在 `--kind line` 下把主曲线与
插图连成一条跨图折线（出现大跨度的水平跳变）。

**根因**：期刊常把"近阈放大插图"放在同图角上，插图曲线与主曲线**同色**，且矢量图里
**插图框往往没有填充** ⇒ 两块同色区域在颜色掩码里连成**一个**连通域 ⇒ 形态判别失败（见 B10）。

**处置**（从 PDF 矢量层拿插图框，确定性排除，不猜）：

```python
import fitz
page = fitz.open("paper.pdf")[6]          # 0 起
for d in page.get_drawings():             # 插图框 = 不与主轴线对齐的矩形
    print(d["rect"])
# 框换算到裁剪图坐标后置白，或用 --region 精确排除该矩形
```

**置白必须自证无损**，两项同时成立才可声称"排除插图无损"：

1. `置白前红像素数 − 置白后红像素数` **恰等于插图框内的红像素数**（实测 2873 px）。
2. 主曲线被遮挡列的行号区间与插图行号区间**无重叠**（实测 25–130 vs 802–1145）。

排除后**显式加 `--kind line`**，不要再让 auto 判别介入。

| PDF 真实文献冒烟 | `test_pdf_smoke.py` | 真实文献能力探测（**文献缺失则跳过计通过**，24 项） |

**E1a. `$PY` 必须是受管 venv，不能用裸解释器。** 裸解释器
（`.../versions/3.13.12/python.exe`）缺 `pymupdf` 与 `openpyxl`，会让 **5 个阶段同时报错**：
PDF 单元测试、API 精度验证、CLI 冒烟、PDF 真实文献冒烟、夹具生成。**这看起来极像代码
回归**（实测被误判过一次），实际只是解释器选错。判据：输出里出现
`No module named 'pymupdf'` 或 `（跳过 XLSX 内部校验：未安装 openpyxl）` → 先换解释器，
不要开始查代码。用受管 venv 时这两行**都不应出现**，且各阶段检查数为
37 / 53 / 81 / 80 / 24（合计 275），零失败。

任一阶段非 0 退出即为失败。**注意脚本必须自己返回退出码**——曾出现
`verify_accuracy.py` 的 `main()` 没有返回值、序列数核对失败仍报"通过"的情况，
等于测试形同虚设。新增阶段时务必确认 `sys.exit(main())`。

### E1b. 为什么同时需要单元测试和图形测试

**机制类缺陷必须用单元测试锁定，图形测试只作补充。**

原因：图形测试依赖 matplotlib 光栅化的**偶然结果**。实测同一个缺陷（浅色候选色吞网格线）
在两种图几何下表现不同——判据是「光晕色到网格灰的距离 < tol=64」：

```
subplots_adjust 版：光晕 (244,200,200)，距离 52.9  → 触发缺陷
tight_layout 版：   光晕 (241,184,184)，距离 67.2  → 不触发
```

于是"换个图就不覆盖了"，测试失去意义。`test_extract_units.py` 把这些机制写成与渲染
无关的确定性断言（直接构造纯色芯/光晕/网格灰三种颜色），才能真正锁住修复。

**判据**：若某缺陷的表现依赖于图像渲染的偶然数值（颜色量化、抗锯齿强度、图尺寸），
就不要只靠图形测试——补一条直接调用被测函数的单元测试。

### E2. 新增了 CLI 参数或改了默认值

必须同步检查：

1. `cli.py` 中该参数在**各子命令**里的默认值是否一致（`detect` 与 `extract` 是两个独立定义）
2. `tests/test_cli_smoke.py` 是否覆盖到该参数的默认路径
3. 本文件与 `SKILL.md` 中对默认值的描述是否已更新

### E3. 新增了测试用例图

在 `tests/make_testcases.py` 中新增 `fig_x()` 并登记到 `main()` 的 `cases` 列表。
**必须使用固定随机种子**（现有用例用 `default_rng(7)` / `default_rng(11)`），否则每次
生成的图不同，真值不再可比，测试失去意义。

### E4. 修改了提取算法

重点回归以下指标（`tests/verify_out/accuracy.json`）：

- 各用例的**检出序列数**是否仍与真值一致（`E/auto-color` 行）
- 散点用例 RMSE 是否仍在 0.44 – 1.09px 区间
- GetData 往返偏差是否仍 < 1e-3（CLI 冒烟测试会打印实测值）

## BW. 黑白线画引擎（零彩色图）

配套原理与阈值见 `SPEC/bw-line-separation.md`；机制类锁定见 `tests/test_bwline_units.py`。

### BW1. 同色多曲线只出一条「并集」

**现象**：图上明显有四条曲线，`extract` 只输出 1 条，点数与区域宽度同量级。

**根因**：该图**彩色像素 = 0**（纯黑白线画），颜色轴上没有任何可分信息。
`dominant_colors` 只能给出一种色（黑），于是四条曲线的像素被并成一条。

```python
import numpy as np
from PIL import Image
from chartdigit import separate_bw, stroke_dictionary

rgb = np.asarray(Image.open("figure.png").convert("RGB"))
print(stroke_dictionary(rgb, (46, 14, 616, 420)))
# {"has_color": false, "color_pixels": 0, "n_series": 4,
#  "width_classes": [2.2, 4.4], "verdict": "零彩色：黑白线画引擎适用", ...}
```

**处置**：改走 `separate_bw()`。**不要**试图靠调 `--tol` / `--colors` 解决 ——
零彩色时颜色轴是空的，调参不可能造出可分信息。

### BW2. 粗虚线旁边多出一条「幽灵细线」

**现象**：检出轨道数比图上曲线数多，多出的那条与某条**粗虚线位置重合**、
颜色同黑、点数只有几十。

**根因**：**虚线末端列**的测宽偏低。列内墨段长度为 L 时，段内 EDT 的上界是
`⌈(L+1)/2⌉` —— 末端列只切到极短一截，EDT 由"段多长"决定而非"笔画多宽"，
于是粗虚线的端列被量成细线宽度，被归入细线类，沿粗虚线长出一条幽灵轨道。
（历史实测：BW-B 长出 39 点、BW-D 长出 69 点。）

**已修**：`column_samples` 沿 x 做 `±w_win=2` 的宽度局部取大。
若仍出现，调大 `w_win`（`separate_bw(..., )` 需经 `column_samples` 调用）。

> **反例留档：不要用"末端列比例"作轨道闸门。** 曾实现"某轨道过半样本是
> `censored` 就整条丢弃"，实测**误删真曲线** —— 全部样本中 52% 被标为 `censored`，
> 因为 EDT 只有 `{2, 2.83, 3.46, 4.0, …}` 若干档，斜笔画相邻两列本就常跨档。
> BW-D 因此从正确的 4 条掉到 2 条。**正确做法是在源头修**（见上）。

### BW3. 被遮挡曲线的半段不见了

**现象**：一条实线被图例框挡成两段，输出只有右半段，**缺口数为 0**，
看起来像"这条线本来就只有右半段"。

**根因（历史缺陷，已修）**：`track_samples` 的"整列无墨"分支只累加 `dead`
并**直接过滤**掉超时轨道，没走 `finished.append` —— 静默丢数据。
锁死测试：`test_bwline_units.py::test_occluded_curve_keeps_both_sides`。

**若复现**：检查 `meta["joined_by"]`。左半段与右半段应被接回同一条轨道，
`joined_by` 为 `extrapolation` 或 `isolated-pair`，且 `n_gaps ≥ 1`。

### BW4. 实线被判成「虚线」

**现象**：连续的实线，`meta["dash"] == "dashed"`。

**根因**：分段阈值过严。`min_gap_cols=2` 会把**单列缺失**当成断开，
而单列缺失在交叉区（合并段被归属给另一条曲线）与抗锯齿抖动处频繁发生 ——
历史实测 BW-C 的实线被切成 34 段，段数密度 6.0 越过虚线判据。

**判据**：看 `meta["n_segments"]`。实线应在个位数；若 `n_segments` 与
`len(points)/100` 同量级，说明是**碎片化**而不是真虚线。
`classify_dash` 用「段数 / 百像素 ≥ 1.8 且段数 ≥ 4」判定，必要时调 `MIN_DASH_DENSITY`。

### BW5. 被遮挡的实线被判成「虚线」

**现象**：一个或多个大缺口，`dash == "dashed"`。

**根因**：判据被换成"缺口长度"了。**这是错的方向** —— 遮挡缺口可能比虚线间隙
**更短**，也可能更长，长度不可用。唯一稳定的差异是**段数密度**（虚线约
7.9 段/100px，遮挡实线约 0.36 段/100px，差一个数量级）。

**处置**：确认 `classify_dash` 用的是密度而非长度；见
`test_bwline_units.py::test_dash_vs_occlusion`（含"缺口 2px 的遮挡仍判 solid"用例）。

### BW6. 引擎在彩色图上返回空表

**现象**：`separate_bw()` 返回 `[]`，但图上看得出曲线。

**根因**：**这是设计行为，不是故障。** 彩色像素 ≥ 50 时黑白引擎主动让位 ——
有颜色轴时颜色才是正确的分离轴，两个引擎同时出结果会给出两套互相打架的答案。

**处置**：改用 `extract_series()`。确需强制黑白路径时用
`separate_bw(..., allow_color=True)`（逃生门，不推荐）。

### BW7. 四条曲线只出了三条（或两条）

**现象**：轨道数少于真值曲线数，且**没有**报错。

**三个已知根因**（都曾真实发生，都已有锁定测试）：

1. **直方图末桶被排除** → 主峰漏检 → 类中心被陪衬峰拖走 → 该类全部样本被
   判为"不属于任何类" → 整条曲线消失。见 `test_end_to_end_minimal`。
2. **类中心取算术平均** → 同一组内峰高差百倍时被陪衬峰拖偏。应**按峰高加权**。
3. **`w_tol` 过紧** → 测得宽度落不回任何类。默认 0.35；无抗锯齿的二值图上
   EDT 只有整数档，跨度大，可放宽到 0.5。

### BW8. `width_px` 与我按 `linewidth` 算出来的对不上

**现象**：matplotlib 里 `lw=1.0`（100 dpi 下 1.39 px），引擎报 `width_px=2.2`。

**根因**：**这是预期行为。** EDT 只在像素格点取值，`W` 只能取
`{2, 2.83(=2√2), 3.46, 4, 4.47, 5.66, 6, …}` 等离散档；此外抗锯齿像素被算进墨里，
奇数宽的栅格带还有 **+1 固有偏置**（宽 w 的带栅格成 `2⌊w/2⌋+1` 像素后 `2·EDT = band+1`）。

**处置**：`width_px` **只用于判定"哪条更粗"**，不得当作物理线宽写入下游或论文。
计量级测宽列为 S3。

### BW9. 曲线以浅角相切，多出一条几十点的碎轨道

**现象**：肉眼 2 条曲线，引擎报 3 条。多出来的那条点很少（几十点）、`dash` 常为
`unknown`、名字与主轨道同宽，`verify_bw_accuracy` 的"一一对应"检查会报
「多条轨道指向同一真值曲线」。

**根因**（自审实测确认）：浅角相切时，细线有一段与粗线的墨团**连成一体**，因而
被测成粗线宽度 → 分进粗线类 → 长出一条独立短轨道。`dedupe_tracks` 只在
**同一个宽度类内**比较，故漏删。这是 S1 已知缺陷（SPEC §7 第 11 条 / §11.5 H2），
尚无自动警示。

**处置**：核对"序列数 vs 肉眼可见曲线数"；不一致时把点数最少的轨道视为可疑，
或整体转 `getdata` 人工兜底。**不要**直接把 3 条都交付。

### BW10. 两条线宽相近的曲线相交，序列数翻倍

**现象**：肉眼 2 条，引擎报 4 条（名字带 `#2`/`#3` 之类后缀），两条各被拆成两段。

**根因**（自审实测确认）：两线宽比低于 `merge_rel=0.35` 时宽度类**退化成一个**，
主分离轴失效；此时两条曲线各被拆成 2 条轨道，而 `merge_tracks` 要求缺口为正、
`_bridge_isolated_pairs` 要求"恰好两条"，两道兜底都不成立。SPEC §7 第 12 条。

**处置**：同 BW9 —— 核对序列数与肉眼可见数，不一致即转人工。也可显式传更小的
`w_tol` 之外的参数前先看 `stroke_dictionary` 的 `width_classes`：若只有 1 类而
平行轨道数 > 1，说明**宽度轴已失效**，此时的结果不可信。

### BW11. 同宽同划线的两条线被合成一条（并集）

**现象**：引擎只输出 1 条，而图上明明有 2 条。该序列的 `width_px` 明显偏大
（约为单线的 2 倍）。

**根因**：两条曲线沿 x **墨迹相连**（相贴或长距离重合），物理上确已不可分辨，
引擎输出并集。**注意：这不是"同线宽 + 同划线"就必然发生** —— 自审实测两条
同宽同划线**交叉**的曲线仍能正确分为 2 条（中位误差 0.62–0.67 px）。

**处置**：**不得把并集当真值**。转 `getdata` 人工逐条点取。
`Series.meta["identity_warning"]` **可能**为 `True`（当合并区被记为交叉、
或接续标记非 `trace` 时），且该序列的 `width_px` 会明显偏大 —— 二者都只是
**线索而非保证**，最终仍须靠"序列数 vs 肉眼可见曲线数"发现。

> **与 BW13 的区别**：BW11 是**合成 1 条**（序列数变少）；BW13 是**序列数正确
> 但身份互换**。后者更隐蔽，因为"序列数对不对"这一最常用的自检**看不见它**。
> 参见 BW13 的双口径判据。

### BW12. 零彩色图却返回空表

**现象**：明明是一张黑白线画图，`separate_bw` 返回 `[]`，也不报错。

**排查顺序**：

1. **区域是否含彩色像素**（≥ `min_color_pixels`，默认 50）→ 引擎按设计让位。
   用 `stroke_dictionary()` 看 `color_pixels` 与 `verdict`。
2. **`trim_frame` 是否吃掉了全部墨迹**：`frame_trim_px=3` 会清掉区域四边 3 px，
   区域本身很小时（< 8 px）会清空。调小该值重试。
3. **背景估计是否反了**（自审发现）：`binarize` 取逐通道**中位数**作背景；
   若区域内**墨多于背景**（实心填充、深色扫描件），中位数即墨色 → 差分为 0 →
   无墨迹 → 静默返回空表。**这正是本项目面向的 2000 年前后印刷期刊扫描件的风险。**
   处置：先用 Pillow 量一遍区域内的暗像素占比，若 > 50% 则显式传
   `background=(255,255,255)`（或先反相）再调用。SPEC §7 第 14 条。
4. 图例文字 / 轴框是否被当成了墨（属 S2 的掩码问题）。

### BW13. **序列数正确、点也都在曲线上，但两条序列的身份互相换了**

**现象**：抽出序列数 = 肉眼可见曲线数，逐点误差也小（位置中位 < 1 px），
**但两条序列在某一处交叉之后互换了身份** —— 前半段 A 属于曲线 1、后半段 A 属于曲线 2。
自审二期实测（H5 近等宽实线两次交叉）：位置口径 P95 **1.34 px**、
身份口径 P95 **13.2 px**；H6 同宽同划线：位置 P95 **1.40**、身份 P95 **64.0**。

**为什么会被"骗过去"**：只看"序列数对不对""点位偏不偏"**看不见**这个缺陷。
必须**同时**用两个口径衡量：

| 口径 | 定义 | 反映什么 |
|------|------|---------|
| **位置** | 点到**最近**真值曲线的距离 | 点是否落在真实曲线上 → 决定能否绘图/拟合 |
| **身份** | 点到**被匹配那条**曲线的距离 | 该序列是否始终是同一条曲线 → 决定能否分曲线解读 |

**判据**：若"位置优秀 + 身份差 + 错配点**连成连续区间**（而非集中在交叉点
±若干像素）"→ 这是**跨缺口接错对象**，不是局部歧义。

**根因（自审二期已实证）**：两条曲线在交叉**之前约 15 px 墨迹就物理相连**，
合成一个墨团（宽度 ≈ 1.5 倍笔画宽）→ 两条轨道在合并段内**看到的是同一个 y**
→ 轨道死亡 → `merge_tracks` 用「长缺口几何相容」判据跨 **109 px** 配对 →
**接上了另一条曲线**。该错误配对由弦斜率判据（中值定理）放行，
而中值定理的约束力**随缺口长度衰减**，无法区分"陡而连续"与"长而错配"。

**处置**：

1. **看 `Series.meta["identity_warning"]`**。这类序列实测**全部为 `True`**
   （判据：过交叉区 / 同类序列在 x 上重叠 / `joined_by != "trace"`）。
   遇到 `True` 即要求人工核对。
2. **按用途分流**：只做绘图/拟合 → 可直接用（位置可信）；
   需按曲线分别解读 → **必须**人工核对或转 `getdata` 逐条点取。
3. **交付说明必须写明双口径**，不得只报"序列数正确"。

**不要尝试的三种做法**（自审二期逐一实验证否，见 SPEC §13.3）：

- ❌ 调大 `share_relax`：`shared` 列数 0→51，身份 P95 只从 13.2 降到 12.5，且序列数 2→3。
- ❌ 给缺口判据加长度上限：能拦住错误配对，但代价是**过分裂**（2→3）。
- ❌ 放宽 `w_tol`：会破坏主分离轴（BW-A / BW-C 依赖它）。

**修复方向（须单独立项）**：合并段内**冻结斜率**（不 `refresh`），按冻结斜率外推
做**分支投票**；`merge_tracks` 增**竞争性判据**（右端存在更近同类端点时不得跨更长
缺口配对）。参见 SPEC §13.5。

## F. 通用诊断流程

出现任何异常，**先跑这两条**：

```bash
# 1. 环境是否正常
chartdigit.py doctor

# 2. 检测结果长什么样（务必看图）
chartdigit.py detect fig.png --diag diag.png --json
```

`--diag` 诊断图会叠加显示：检出面板框、轴线、刻度线、提取到的数据点。90% 的问题看一眼诊断图就能定位——通常是"检出的框不在数据区上"或"提取点没贴住曲线"。

若诊断图正常但数值不对，则问题在**标定**：检查报告的锚点与往返误差，确认 `--xlim/--ylim` 是否与图上刻度一致。

## G. 反馈路径

修复本技能的问题时，请同时更新本文件与 `references/algorithms.md` 的"实测失败模式"章节——这样下一个遇到同类问题的人能直接查到根因，而不是重新踩一遍。

若某类问题**本可由测试拦住却没拦住**，除修 bug 外还须在 `tests/` 中补一条覆盖该口径的用例。
本轮两个缺陷（散点光晕、候选色吞背景）都是这么暴露的：它们躲过了走 API 且显式传色的
旧验证脚本，补上 `E/auto-color` 模式后才现形。
