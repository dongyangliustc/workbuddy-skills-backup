# 稿件章节内容定位审计（section placement / narrative logic）

## 何时用

- 用户认为"某节读起来不像它应有的样子"——典型：**Methods 像软件清单**、**Results 像方法学论文**。
- 用户抱怨"重复感"，或"同一件事说了很多遍"。
- 需要为某节建立骨架，但不确定哪些内容该留在正文、哪些下沉 SI。
- 稿件要"增色"（补理论推导、补误差传递），但怕加重重复。

**不适用**：纯语言润色（`nature-polishing`）；纯文档定位与批注提取（`docx-toolkit`，读 `references/locate-and-comment.md`）；参考文献核验（`nature-ref-verifier`）。

## 核心判据：先立口径，再谈对错

**"允许写"与"写在哪"是两个独立问题。** 任何审阅必须先给出内容分类口径，否则"写多了"的批评无法落地。

| 类别 | 典型内容 | 允许位置 |
|---|---|---|
| **首次阐述** | 问题存在的证据（该逻辑首次出现处） | 引言（**一次**） |
| **路线图** | "本文做了什么" | 引言末段（**一次**） |
| **方法原理** | 概念定义、公式、算法 | **Methods** |
| **操作细节** | 积分/加权/拟合步骤 | **Methods** |
| **不确定度** | 误差数值、置信区间、传递关系 | **Methods + SI** |
| **方法自评** | "我们优于前人" | Methods（正文不重复；摘要豁免） |
| **理论推导** | 本文的智识贡献（新概念框架、新模型） | **Results（必须留，删了就伤论证）** |

**错配判据**：某类内容在**应然位置缺席**，却在**偶然位置反复出现** → 空间错配。

**处置铁律：成对操作。** 正文每删一条方法性表述，应然位置必须有**更完整的唯一落位**。
- 只删不补 → 稿件失去方法学分量；
- 只补不删 → 重复感加剧。
若用户提出"某节单薄"与"正文重复"两件事，先判断它们是**同一处错配的两个症状**（多数情况下是），再成对处置——这比分开处理更省事，也更能说服用户。

## 三条硬指标（自证诊断，不靠印象）

1. **关键词命中分布**：把 `uncertain|error|accuracy|convergence|RMSD|bias` 之类扫全文，列出**命中段落清单**，再看**目标节内命中数**。目标节 0 命中 ⇒ 该节空心化（不确定度全被推到正文）。
2. **公式与图形对象计数**：统计 `oMath` / `oMathPara` / `w:drawing`。一篇方法学定位的稿件若**全文只有 1 个公式**，"平平无奇"就有硬证据，而不是主观印象。
3. **交叉引用覆盖**：SI/附表被正文引用次数。**存在但 0 引用**（或引错编号）是结构性缺口，编辑与审稿人必抓。

## 工作流

### 1. 确认母本（不可跳）

手稿目录常有多个近似版本与旧提取件。**先实测 md5 + mtime + 顶层段落数**，再动手。
若目录里有 `_master_now.md` / `_final_check.md` 之类的文本快照，**先验证它是否落后于母本**（用一句你自己知道"已改/未改"的句子去命中它）。

### 2. 只读抽取（绝不写源 docx）

```bash
PY="C:/Users/Administrator.DESKTOP-7RU274I/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
"$PY" docx_readonly_dump.py "<母本.docx>" "<out.txt>" --with-tables   # 全文 + [P00xx] 顶层段落号
"$PY" dump_paras.py                                                   # 指定段落完整/折行 + SI 引用扫描
"$PY" probe_omml.py                                                   # oMath / drawing 计数（防误报）
```

### 3. 逐段打标

对正文每一段标注上表的**类别**，并写一句**判定**（✅保留 / ⚠️收缩 / 🟠下沉 / 🔴改）。产出"段落 | 段首原句（锚点） | 内容摘要 | 类别 | 判定"五列表。
**关键**：区分"真正需要动的段落"与"依赖未定义概念的结果段"。后者的问题不是"写多了"，而是 Methods 未定义该概念——不要误删。

### 4. 建双线映射

把正文的论证骨架（如"三因素"）与待重构的方法骨架并排，让**每一根正文骨架都能落在一个方法子节上**：

```
Results 线： 现象 → [因素1] → [因素2] → [因素3] → 速率 → 模型
                      │          │          │        │
Methods 线：       M1         M2         M3       M4
                                                  M5（不确定度与传递）
```
映射建不起来的那一块，就是"Methods 无骨架"的证据。

### 5. 输出（四块，见模板）

## 输出模板

**A. 一句话结论**——点明根因，并把用户的多个诉求归因到同一处（若是）。

**B. 逐段台账**——五列表（见 §3）。

**C. 应然位置的重构骨架**——每个子节给四项：`目的 / 必须回答的问题 / 与正文的接口（吸收哪句）/ 现状缺口`。
把用户想"增色"的两大核心（理论推导、不确定度传递）各设**独立子节**，并先给骨架再问详略。

**D. 硬错误清单**——**事实性与逻辑错误排在格式问题之前**；每条给：现句原文 → 问题 → 建议改写 → 依据。
再附"需用户裁定"的问题（通常 2–3 条），并给出各自利弊，不要替用户决定。

## 陷阱（实测教训）

1. **文本抽取漏 OMML / 图形**：python-docx 只抓 `<w:t>`，公式与图片**不入文本**。不探针就下"公式缺失"的结论会**误报**。先跑 `probe_omml.py`。
2. **长行被截断**：单段超过约 2000 字符会被行式读取器截断（表现为段尾 `[truncated]`）。必须**按句折行重取**，否则会漏掉段尾——而段尾常常正是"评价句"与"图引用"所在。
3. **顶层段落编号 ≠ Word 页码/行号**：Word 行号不能跨页累加。**一律以"段首原句"作锚点**，并在输出开头声明编号口径。
4. **快照不是母本**：旧提取件会让人误判"某句已删/未删"。凡引用"现状"，只能引自**本轮从母本实抽**的文本。
5. **无支撑引用**：正文引用了某节从未给出的量（如"method uncertainty"、"1.5% accuracy"）→ 高价值发现，务必单列。
6. **逻辑方向复核**：断言可能与其支撑数据**方向相反**（例："劈裂能 far exceeding the uncertainty" 实际是"劈裂能落在不确定度之内"）。**方向错误优先于一切风格问题**。
7. **别把"重复"当唯一问题**：同一概念在"首次阐述 + Methods"各一次是**合规**的，第三次才算超限。逐条数出现次数，再判。

## 复用资产

- `dump_paras.py`（指定段落完整/折行导出 + SI 引用扫描）
- `probe_omml.py`（OMML 公式与图形对象计数）
