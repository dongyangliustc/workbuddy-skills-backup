# 假覆盖审计

## 核心命题

**测试通过 ≠ 用户路径可用。** 测试的绿色只说明"被测的那些路径是好的"。当被测路径与
用户路径不是同一条时，绿色毫无意义。有两类假覆盖，都必须审计。

| 类型 | 假覆盖的来源 | 判据 |
|------|-------------|------|
| **口径不一致** | 测试走的接口 ≠ 用户走的接口 | 验证脚本调的是库函数还是 CLI 子进程？默认参数被执行了吗？ |
| **触发偶然** | 缺陷只在特定数据/渲染数值下触发 | 缺陷表现是否依赖量化、抗锯齿强度、图尺寸等偶然量？ |
| **量不可达** | 判据/断言在真实量程内**不可能满足**，而测试在**另一个刻度**上验证 | 被测判据的单位口径与调用方传入的口径是否一致？测试夹具的数值尺度是否等于真实尺度？ |

三类在实测中都出现过，下面分别给出可执行的审计方法。

---

## 类型一：口径不一致

### 案例

某图表数字化工具的验证脚本走 Python API，一切正常、精度达标、32 项检查全绿；但用户通过
CLI 调用多子图提取时**全部失败**。根因是 `extract` 子命令的 `--min-ratio` 默认值被写成
`0.55`，而 `detect` 子命令和 API 都是 `None`（启用多尺度自适应搜索）。`0.55` 恰好使
2×2 布局检出 **0 个面板**——而 `detect` 单独运行却报告 4 个面板，现象自相矛盾，极易被
误判为"检测算法有问题"而去改错地方。

这个缺陷躲过了全部 API 层测试，因为**缺陷只存在于默认值里，而 API 测试从不使用默认值**。

### 三类必须审计的漂移

**1. 默认值漂移（最高危）**

同一语义的参数在**多个 `add_argument`**（或其他定义点）中各写默认值，容易只有一个改对。

```bash
grep -n "min-ratio\|min_ratio" cli.py
# 期望：所有定义点默认值一致；不一致即为缺陷
```

判据：同一参数在多处定义，默认值不同且未在帮助文本中说明差异 → 缺陷。
修法：统一默认值；若确实需要不同默认，必须在 `--help` 文案里写明，否则属未声明行为。

**2. 口径覆盖漂移**

验证用例全部走 API 且**显式传参**，因此自动路径（默认参数 + 自动推断）从未被执行。

```python
# 危险写法：显式传了 colors，绕过了自动颜色聚类
extract_series(rgb, box, colors=[C_RED, C_BLUE], kind="scatter", tol=90)
```

判据：验证脚本中被测函数的可选参数是否**全部**被显式指定 → 是则是"假覆盖"。
修法：每个用例至少再跑一遍不传可选项的完整默认路径，并作为独立口径记录。

**3. 处理路径漂移**

CLI 在外层做了一步预处理（内缩边界、单位换算、格式转换），验证脚本直接猜 API 调用，
少了这一步，于是测出与 CLI 不同的结果（通常表现为"多检出若干序列/多出若干条目"）。

实测：CLI 默认 `--inset 2` 把提取区域向内缩 2px 以避开轴框线；验证脚本未内缩，于是把
轴框线当成数据，每个面板都多检出 1 条序列，看起来像"去重算法失效"。

判据：验证脚本中是否存在与 CLI 重复实现的预处理逻辑 → 存在则迟早漂移。
修法：把逻辑抽成共享函数，让两边调用同一个，而不是在测试里平行复刻。

**4. 隐式参数漂移：生产值藏在调用方，库默认值是另一个值，且**两处都不在"单一权威配置块"里

前三类是"同一参数多处定义不一致"；这一类更隐蔽——**参数根本不在声明面上**，而是由某个调用脚本隐式传入。
任何**配置校验器都只检查它自己知道的键**，因此这类漂移对全部守卫**结构性不可见**。

实测（2026-09-28，球面波光电离求解器 S8-C 判据 (5)）：
- 生产结果由 `multicentre_cross_section(..., normalise_method=...)` 决定；生产用 `"kmatrix_simul"`，
  **只写在两个基准驱动脚本里**（`phase_k_ap_ch2o_benchmark.py:304`、`phase_k_ap_ch4_benchmark.py:327`），
  而**库默认是 `"diagonal"`**，且该参数**不出现在 `production_config.yaml` / 参数标准文档**中。
- 后果：同一缓存、同一能量、其余参数全同，**σ_L 在两种归一化间差 1–3 个数量级**
  （11 eV：1.78 vs 1413.8 Mb = 794×）；一个"稳定性门判据"的通过与否**完全由这个未被声明的参数决定**
  （`diagonal` 下 V/L = 0.839–0.887 全通过；`kmatrix_simul` 下散乱到 0.31–43.8）。
- 附带发现：该参数重建解时经 `inv(A_reg)`，使"判据 A（谱条件数）"与"判据 B（L/V 一致）"**并非独立**——
  即两个本该互相印证的门判据其实是同一条链上的上下游（实测 r=0.639）。

判据（三条任一成立即缺陷）：
1. 同一语义的参数在"库默认"与"生产调用点"取值不同，且**未出现在项目的单一权威配置块**中；
2. 该参数对最终结果的影响 ≥ 一个可观测阈值（本例是 1–3 个数量级）；
3. 守护/校验套件**没有任何用例**覆盖"生产取值 vs 库默认取值"的差异。

修法（按代价从低到高）：
1. **纯记录**：把该参数显式写入配置真源（不改行为）→ 闭合可追溯性；
2. **守卫**：对该参数的后果加非静默告警（如"输出越界即 warn 并记录所用取值"）；
3. **独立性检查**：凡两个门判据**共用同一条计算链**（此处经同一个 `inv(A_reg)`），
   必须证明或声明其相关性，否则"两个判据都通过"不构成互相印证。

**实现配方（已被验证，2026-09-29，球面波 Run #226，规则 R7）**——"声明 + 漂移守卫"三步：

1. **声明块**（写入单一权威配置，**值 = 生产实际值 ⇒ 零行为改动、免重基线**）：
   记录 `method` / `allowed_methods` / `library_default` / **`production_callers`（受守卫的调用文件清单）**。
   ⚠️ **作用域陷阱（实测踩过）**：库常有多份默认值——本例 `multicentre_cross_section`→`diagonal`、
   `h2_multicentre_xs`→`diagonal`，但专用包装 `h_atom_multicentre_xs`→**`analytic`**。
   故 `library_default` 必须**限定到具体函数**，否则声明本身就是错的（首版测试即因此 FAIL 并暴露该事实）。
2. **漂移守卫**（校验器新增分支）：
   - 缺块 / 缺键 / 值不在白名单 ⇒ **ERROR**；
   - **扫描每个 `production_callers` 文件里的 `param="X"` 字面量，任一 `X ≠ 声明值` ⇒ ERROR**
     （这是最高价值的一条：它拦住"改了驱动忘改配置"与反向漂移）；
   - `声明值 ≠ library_default` ⇒ WARN（提示调用方**必须显式传参**，省略即静默换物理）。
   把"比较"逻辑抽成**纯函数**（文件 I/O 与比较分离），以满足"合成校验器用例必须内存内"。
3. **负控（防空测试，必须双向）**：合成一个"漂移驱动" ⇒ 断言 ERROR **确实触发**；
   把声明值改成库默认 ⇒ 断言该 WARN **确实消失**（计数 1→0）。只测正例等于没测。
   再加一条**库源码漂移锁**：直读库签名（正则）断言 `library_default` 声明仍与真实默认一致——
   防止将来库改默认值而配置里的声明变成陈旧断言。

⭐ **通用结论**：**任何决定生产结果的参数，都必须验证其出现在单一权威配置块内**（C-8 类）。
配置校验器天生只检查它已知的键 ⇒ 白名单之外的一阶参数对**每一个**守卫都不可见。

```bash
# 快速筛查：列出所有"库默认值 + 生产调用点"可能不一致的可选参数
grep -rn "def .*(.*=.*," lib/*.py | grep -v "^.*#"        # 有默认值的形参
grep -rn "your_param_name" --include=*.py .               # 所有调用点是否显式传参
python -c "import yaml,sys; c=yaml.safe_load(open('config.yaml')); print('your_param_name' in str(c))"
```

### 操作流程

**第一步：列出全部口径**

| 口径 | 用户用吗 | 测试覆盖吗 |
|------|---------|-----------|
| CLI 子命令 + 默认参数 | 是（主） | ？ |
| Python API + 显式传参 | 有时 | 通常是 |
| Python API + 默认参数 | 有时 | ？ |

凡是"用户用，但测试不覆盖"的格子，都是缺陷的藏身处。

**第二步：写"用户口径"冒烟测试**

以**子进程**方式调用 CLI，而不是 `import` 后调函数——这是本质区别。

```python
def run(args):
    return subprocess.run([str(PY), str(ENTRY), *args],
                          capture_output=True, text=True,
                          encoding="utf-8", errors="replace")

p = run(["extract", img, "--xlim", "0", "10", "--ylim", "0", "4"])
assert p.returncode == 0, p.stderr
```

必须断言三件事：
1. 退出码为 0（非 0 就是用户看到的失败）
2. 声称的产物文件确实生成
3. **业务计数**与期望一致（序列数、行数、记录数）——这一项才抓得住"跑通了但结果错"

**第三步：把默认值纳入断言** —— 每个有默认值的参数，至少有一个用例不传它。

## 类型二：触发偶然

### 案例

某抗锯齿候选色会在 `tol=64` 的颜色容差内吞掉浅灰网格线，产生一条覆盖全图的伪序列。
端到端图形测试本该抓住它，但**同一个缺陷在两种图几何下表现不同**——判据是
"光晕色到网格灰的距离是否小于 64"：

| 图几何 | 光晕色 | 到网格灰 (231,231,231) | 结果 |
|--------|--------|----------------------|------|
| `subplots_adjust` 版 | (244,200,200) | 52.9 | 触发缺陷 |
| `tight_layout` 版 | (241,184,184) | 67.2 | 不触发 |

也就是说，**重写测试用例图（哪怕只是改了布局）就可能让覆盖消失**。这类测试的绿色
是不可信的。

### 识别特征

缺陷表现依赖下列任一偶然量 → 归入本类：

- 颜色量化结果（同一语义的颜色落在不同量化桶）
- 抗锯齿强度（由线宽、图尺寸、渲染后端决定）
- 浮点比较的临界（"恰好越过阈值"）
- 随机数（未固定种子）
- 平台/库版本差异

### 处置：机制类缺陷用单元测试锁定

把这个机制**从渲染中剥离**，直接构造输入断言输出：

```python
# 不依赖任何图像：直接构造纯色芯 / 光晕 / 网格灰三种颜色
kept = drop_antialias_colors([CORE_RED, (244, 200, 200), (228, 228, 228)], WHITE)
assert CORE_RED in kept            # 保留纯色芯
assert (244, 200, 200) not in kept # 剔除混合色
assert (228, 228, 228) in kept     # 不误杀网格灰
```

**判据**：缺陷的触发条件若包含图像渲染、随机数或环境相关的偶然数值，就必须有单元测试，
图形/集成测试只作补充。

**同时补一条"否定断言"**：证明修复确实在起作用。例如断言"基础容差 4px 覆盖不到 5px
的偏移"，以说明"按半径放宽容差"是必需的，而不是碰巧通过。

### 一个衍生陷阱：判据本身错了

同一案例中还发现，早期验证脚本用"相对误差 < 1%"作为对数轴的判据，得出"未达标"的
错误结论——而**判据本身就是错的**：对数轴上 1 像素对应**固定的相对误差**，其大小取决于
轴跨几个数量级（跨 5 个数量级时 1px = 3.0%）。于是"3% 的相对误差"其实是完美的。

**教训**：在断言"失败"之前，先验算这个判据在**已知正确的输入**上会给出什么值。
用一组手算可verify的输入标定判据的期望范围，再拿它去判待测实现。

## 报告格式

以编号列表逐条呈现，每条含四项：

```
[N] 现象      <用户能看到什么>
    口径/条件  <哪个口径下出现，哪个口径/数据下正常>
    根因      <文件:行号 + 一句话>
    判据/修法  <可复现的检查命令；改法；并说明"测试能否拦住下一次">
```

"哪个口径下正常"（或"哪个数据下正常"）这一栏不能省——它正是定位缺陷在
"默认值/预处理/参数解析/偶发触发"哪一层的依据。

---

## 常见陷阱

1. **修错地方**：现象是"检测不出面板"，根因在参数默认值。先确认各口径结果是否矛盾，
   矛盾（A 口径正常、B 口径异常）几乎总是指向参数/预处理层，而不是算法层。
2. **帮助文本没写默认值**：`add_argument("--x", type=float, default=0.55)` 不给 `help=`，
   用户无法从 `--help` 看出默认值，缺陷更难发现。**凡非平凡默认值必须写进 `help=`**。
3. **测试里复刻 CLI 逻辑**：见"处理路径漂移"。抽共享函数，不要复制。
4. **测试脚本不返回退出码**：`def main() -> None` 且没有 `sys.exit(main())`，会导致断言
   失败仍以 0 退出——**整个测试形同虚设**。新增测试阶段时务必确认退出码链路。
5. **只测 happy path**：用户口径的失败用例（参数缺失、非法组合）也应至少各有一条。
6. **改完 bug 不补覆盖**：问一句"这个 bug 本可由测试拦住吗"；若不能，必须补用例。
   修 bug 是止血，补覆盖是免疫。

## 类型三：判据在真实量程内不可达（绿灯验证了另一个刻度）

### 案例（2026-09-17，黑白线画分离引擎 S1 自审）

一条"按剖面**显著谷**切分交叉合并段"的判据，声称门槛是"相对期望半宽 `w_hint/2`
归一化"，即谷底须跌到脊线的 **62%**。单元测试直接构造一维剖面（峰高 3.0 配
`w_hint=6.0`）验证"深谷切 2 段、浅谷不切"，**全绿**。

审计发现该机制**在真实路径上从不触发**：五个用例共 **10 404 次调用触发 0 次**。

根因是**单位口径漂移**：调用方传入的剖面是 `2·EDT`（**宽度**刻度，脊线 ≈ `w_hint`），
而门槛按半宽刻度写成 `0.31·w_hint` —— 两者差 2 倍。严重的是漂移之外还有**硬下限**：
`2·EDT` 的最小可能值是 **2.0**（任何墨像素的 EDT ≥ 1），于是判据
`0.31·w_hint > 2.0` 只在 `w_hint > 6.45 px` 时才可能被满足。
**对常见的 1–3 px 细线，该判据数学上不可满足。**

而单元测试喂入的是**原始 EDT 刻度**（峰 3.0 对标 `w_hint=6.0`），恰好落在
"可满足"的那一侧 —— 于是绿灯**不覆盖**真实路径。这类假覆盖的隐蔽之处在于：
测试的**构造是对的、断言是对的、数字是对的**，唯一错的是"测试的数值尺度不等于
运行时的数值尺度"。

### 判据（三条都要过）

1. **单位核对**：把判据里的每个阈值与被比较的量**各写一遍量纲/刻度**，
   看两边是否同为"宽度"或同为"EDT"。凡出现 `x/2`、`2*x` 这类因子，重点怀疑。
   本项目的历史是：修掉一处 `2·EDT` 被再乘 2 的缺陷时，**只改了取值处、没改门槛处**，
   留下了 2 倍口径差。
2. **可满足性下界**：量本身若有硬下限（EDT ≥ 1、像素 ≥ 1、距离 ≥ 0、计数 ≥ 0），
   把门槛与该下限代数比较，算出"判据能被满足"的参数区间。
   若该区间与"实际业务量程"不相交 → 判据**恒不触发**，功能等于不存在。
3. **实证触发率**：给被测函数套一个计数器，跑**全部**既有用例，报告触发次数。
   **触发 0 次的功能必须是"惰性"结论，而不是"已实现"结论。**
   计数器写法（Python）：

   ```python
   import mod
   STATS = {"calls": 0, "hits": 0}
   _orig = mod._suspect_fn
   def spy(*a, **kw):
       STATS["calls"] += 1
       out = _orig(*a, **kw)
       if <判据命中条件>: STATS["hits"] += 1
       return out
   mod._suspect_fn = spy        # 模块内按全局名调用才拦得住
   ```

   注意：**"触发 0 次"不能直接推出"功能无用"** —— 还要做**消融**（见下）
   才能判定它对最终结果的贡献。

### 消融必须做对：摘除的是机制，不是开关

同一案例中，首版消融用"把容许度参数放到极大"来"摘除宽度轴"，结论是"摘除后结果
**逐位不变**"。审计随即发现**该消融无效**：该容许度只控制"是否拒绝样本"，
而实测被拒样本数为 **0**，故放大它**不改变任何样本的归属**。正确做法是
**monkeypatch 上游的分类函数，使它恒返回单一类**，才真正摘除该轴。

> 通用教训：**"把参数调到极端"通常只关掉了开关，关不掉机制。**
> 摘除一个机制的正确方式是让它**不可能产生判别信息**（恒返回同一个值、
> 把输入退化成常量），而不是让它"更宽松/更严格"。

正确的消融结果（本例）才是有价值的：摘除宽度轴后，交叉用例 **2 条塌成 1 条**
（该轴对相交曲线是决定性的），而 y 上分开的用例**逐位不变**（该轴无贡献），
另一用例**序列数不变但划线判错、点数少 17%** —— 说明**只用"序列数 + 精度残差"
评价结果是看不见退化的**，必须补结构属性（划线、点数、一一对应）的断言。

### 附带发现的第二类护栏缺口

**聚合护栏只认退出码，从不校验断言数量。** 实测：一键回归脚本
`run_all.py` 对 `共 N 项检查` 的**引用数为 0**，它仅凭子进程 `returncode` 判定
阶段通过。后果是**一个断言全部失效（打印 0 项）的阶段会被照样报"通过"**，
而"合计 406 项"是人工求和、没有任何机制保护它不被静默削减。

检查方法：

```bash
grep -c "项检查" run_all.py     # = 0 即无一字护栏
```

**加固范式（2026-09-20 已落地并验证，纯加固、不动任何断言）**

1. 主脚本捕获各阶段输出，正则抓 `共 N 项检查`，与一张 **`BASELINE` 基线表**比对：
   - 低于基线 → 失败；
   - **该报数的阶段压根不报数 → 也失败**（报数代码被移除 / 阶段被整体跳过）；
   - 高于基线 → 放行并标出增量（"只增未改"）。
2. **给护栏本身写测试，并钉住两条防静默失效的断言** —— 这是关键，否则
   护栏最隐蔽的失效方式不是逻辑写错，而是**键名漂移**：
   `BASELINE.get(name)` 恒为 `None` → **每次"通过"却什么都不查**。必钉：
   - `BASELINE` 每个键**都存在于阶段表**（改了阶段名就会悬空）；
   - `BASELINE` 每个键**都对应磁盘上真实存在的文件**；
   - 基线小计必须能**复算出**那个对外引用的总数（如"7 阶段 = 406"）。
3. **受控破坏验证（唯一可信的验证方式）**：人为把基线抬高 1 项，
   跑主脚本**必须**报失败。实测结果：退出码 **1**，输出
   `项数 20 < 基线 21 —— 断言被删改`。随后恢复基线。
   —— 只看"通过"证明不了任何事；**必须看到它能拦住**。
4. **数字必须随口径走**：加了护栏自检阶段后，"406"（原 7 阶段）与"426"
   （8 阶段，含护栏自检 20 项）**都正确**，取决于含不含自检。引用时不写口径，
   数字就是错的。汇总行要按"N 个报数阶段 / 另有 M 个不报数"动态表述。

### 附带发现的第三类护栏缺口：**验证工具自身静默降级**

同一轮里又抓到一个更隐蔽的：用于证明"既有断言没被改写"的标签比对脚本
`diff_labels.py`，**正则本身吞标签**。

- 原写法：`^\s*\[(?:OK|FAIL)\]\s+(.+?)(?:\s{2,}.*)?$`（`re.M`）
- 缺陷：**`\s` 包含换行**，故 `\s{2,}` 会匹配 `"\n  "`（换行 + 下一行缩进）
  → 匹配**跨越两行、吞掉下一条标签**。一份 20 条标签的输出只能抽出 **10 条**
  （恰好一半），**且不报任何错**。
- 危害：去重集合变小，但"**丢失 = 0**"**仍然成立**
  ⇒ **结论看似正确、依据实则残缺**（实测 286→296，而非 306）。
- 修法：行内间隔改 `[^\S\n]{2,}`（**只吃水平空白**）；并加**自校验**——
  抽出的标签数必须等于 `[OK]/[FAIL]` 行数，否则**退出码 2、拒绝给结论**。
- 修正后：406 行 → 406 标签、426 行 → 426 标签、丢失 0、新增恰 20。

**通用判据（凡"检查器 / 护栏 / 比对器"都要加）**：

> **它抓到的条目数，必须等于源里的条目数。** 不等就报错退出，
> 宁可拒绝给结论，也不要给一个"看起来对"的结论。

这条与本技能类型一/二/三同源：**一个恒真的判据 = 没有判据**。
区别只在于——前三条的恒真者是被测代码，这条的恒真者是**验证工具自己**。
